# 06 — Signatures, replay & EIP-712 gaps

## SIG-01 — Signed digest omits an economically relevant parameter
**Root cause.** A signature covers most, but not all, of the fields that
matter — a field left out of the digest can be swapped in by whoever
relays the signed message.
**Precedents.** `createAgentWithSigWithNFT()` M-2 (Crestal Network) —
signed `projectId`, `base64RecParam`, `serverURL` but *not*
`privateWorkerAddress` or `tokenId`, letting an attacker couple a
legitimately-signed message with malicious values for the unsigned
fields. `TitlesGraph` M-1 (TITLES Publishing Protocol) — EIP-712 digest
encoding didn't match what common signing tools produce, a related but
distinct correctness bug (signatures generated by standard libraries
became unusable, not exploitable — still worth flagging as it breaks
integrations).
**Detection.** For every signed action, diff "fields the function actually
uses" against "fields included in the hashed struct." Any field used but
not signed is a candidate for this class.

## SIG-02 — Missing nonce / replay protection on a signed action
**Root cause.** A signature can be submitted more than once (or, in
cross-chain settings, replayed on a different context) because nothing
ties it to a single use.
**Precedents.** `updateWorkerDeploymentConfigWithSig()` M-3 (Crestal
Network) — signature replay let an attacker repeatedly transfer funds.
Validator signatures with a zero or already-used timestamp in
`MinterGateway.updateCollateral` (M^0 Minter Gateway H-2/M-2) — the
digest's replay protection was the *timestamp*, and a timestamp of zero,
or a greater timestamp reused, could be replayed.
**Detection.** Identify what the protocol is using as the anti-replay
value (nonce, timestamp, both) and check: (a) it's actually included in
the signed digest, (b) it's checked strictly (not `>=` where `>` was
intended, not skippable at zero), (c) it's invalidated/incremented before
any external call that could reenter.

## SIG-03 — Signature malleability not rejected
**Root cause.** ECDSA signatures have two valid `(r,s,v)` representations
for the same message; if the contract doesn't canonicalize/bound `s`
(OpenZeppelin's `ECDSA` library does this by default — check for a custom
verifier that doesn't), a second valid signature can be derived and reused
somewhere replay protection assumed each signature was unique.
**Precedents.** `TitlesGraph` M-9 (TITLES) — signature malleability
confirmed on a custom verifier path.
**Detection.** Any hand-rolled `ecrecover` usage instead of a vetted
library — check for `s` upper-bound enforcement.

## SIG-04 — `ecrecover` returning the zero address not rejected
**Root cause.** `ecrecover` returns `address(0)` on a malformed signature
instead of reverting. If the recovered signer is compared against a
default/unset storage value (which is also `address(0)`), *any* garbage
signature "verifies" until the real signer is configured.
**Precedents.** DistrictOne M-04 — "any signature is valid before the
issuer address is set," because the issuer address defaults to zero and
isn't checked against zero before comparison.
**Detection.** Every `ecrecover`-based check: confirm the recovered
address is explicitly checked `!= address(0)` in addition to matching the
expected signer.

## Cross-references
`ACC-01` (frontrunnable initializer) often compounds with `SIG-04` when an
unset signer/owner address is the same zero value a malformed signature
recovers to.
